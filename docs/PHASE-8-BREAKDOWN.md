## The finding that matters

**On the PC the game is meant to run on (Windows, Docker Desktop), 100 players is at the edge, not comfortably inside the budgets.** The server carries 100 bots within every budget when run outside Docker (tick p99 5 ms, event loop 15 ms, bandwidth 26 KB/s), and 150 bots with only bandwidth a whisker over (40.8 against 40). Inside Docker Desktop's virtual machine the same code is about 1.7 times slower to send: 100 bots measure tick p99 16 ms (budget 10) and event-loop lag 31 ms (budget 20), with bandwidth (26 KB/s) and the input-to-acknowledgement time (108 ms) inside. 60 bots for 25 minutes met every budget with flat memory. [LOAD-TEST.md](LOAD-TEST.md) has the tables, what was tried that did not help, and what could. **Planning guidance: about 60 to 80 players comfortably on a Windows PC with Docker Desktop; more on a Linux host (the EC2 trial in the plan, phase 9).**

## Steps in detail

1. **The bots** log in the way a person does (an admin makes the account, the bot chooses its password, gets a ticket, says hello), then play at 20 inputs a second, with now and then a sentence, a wave, a sit, a pick-up attempt and a put-back attempt; they measure the time to the server's acknowledgement, the ping, the bytes and snapshots received, and anything that was not understood. A run ends with a table and exit code 1 if a budget is missed.
2. **What the server says about itself** (`GET /api/world`): `tickMs` has `p50Ms`, `p99Ms` (over the last 2000 ticks, 100 seconds), the average and maximum of the last 100, and the count of late ticks; `process` has `rssMb`, `heapMb` and the event-loop lag (`eventLoopP99Ms`, `eventLoopMaxMs`, since the window was last emptied: `GET /api/world?fresh=1` does that, and `npm run bots` calls it before the bots start playing, so a test reads what its own run did while other readers of the page do not disturb it). The histogram records the whole time between two 10 ms timer ticks; the report subtracts the 10 ms.
3. **The short move record.** Most of a snapshot used to be people who are walking, sent as whole records of about 46 bytes though only where they are and which way they face had changed. The server now compares each changed person with what it last sent them: if nothing but position, facing and stride differ, the person goes in the snapshot's new `moves` list (id, x, z, facing, stride: **14 bytes**), otherwise as a whole record as before; after any change that is not only a move the whole record is sent two more times (a snapshot a slow client skipped must not leave it out of date), and a keyframe (once a second) is whole records only, so a client that missed a message recovers. The page's mirror applies a move to the person it already has. A count that claims more moves than there are bytes is refused. Protocol **15**.
4. **Things that did not help, and were not kept:** acknowledgements every second tick, the world 10 times a second, rarer keyframes, a Debian base image. (Each measured, none lowered the tick time inside Docker; LOAD-TEST.md.)
5. **Backups** are plain SQL (`pg_dump --clean --if-exists --no-owner --no-privileges`), so they restore under any user and into any PostgreSQL 16. **The rehearsal** restores the dump into a throwaway container and compares the number of rows of every table and the shape of the saved world (the live world is saved every ten seconds, so its checksum moves; how many people, the save version and the desk order do not). **A restore** refuses without `--yes`, refuses a file that is not a complete `pg_dump` output, writes a safety backup of the current database, stops the server, empties the schema and loads the file in one transaction (a failed load leaves the database as it was), and starts the server again.
6. **Found while doing it:** the final save on a polite stop had never worked (the database connection was closed before the save; see [PHASE-5-BREAKDOWN.md](PHASE-5-BREAKDOWN.md), step 5): a restart lost up to ten seconds. (While doing this, a database test that had been failing since the profile-picture step was found and fixed: the migration list in it was out of date.)
