# Phase 4: players together, in steps

**Status: in progress. Steps 1 to 5 are done; step 6 is next.** This turns phase 4 of [MULTIPLAYER-PLAN.md](MULTIPLAYER-PLAN.md) ("Players together") into steps that are each built and checked before the next, the way phases 2 and 3 were ([PHASE-3-BREAKDOWN.md](PHASE-3-BREAKDOWN.md)).

**Done when (from the plan):** many people walk and sit together, and everyone sees and hears the same things. In practice: your own movement answers the keys at once, you can tell who is who, you can talk to people near you, you can wave, and what happens in the office (an announcement, Hazel's rage) happens for everyone at the same moment.

## What is already there (from phases 2 and 3)

Other people are drawn interpolated about 150 ms in the past; the server owns movement, sitting and who is where; sitting and standing are requests the server accepts or refuses; the office speaks one binary protocol over one Socket.IO event. So phase 4 adds what is missing from the plan's list: **prediction and reconciliation**, **name labels**, **local chat**, **emotes** and **shared events**.

## Decisions

1. **Prediction is simple and tolerant, not exact replay.** The client moves your person at once with the same shared collision and speed rules (`stepPlayer`), sends inputs as it does now, and the server sends back a small personal `ack` message each tick (the number of the last input it used, and where you are). The client compares that with where its own history says it was when it sent that input, and only when the two differ by more than a threshold (0.5 m; an input can be believed for a tick or two longer by the server, so a little difference is normal) does it pull your person toward the server's answer, by half the difference at a time, and snaps if the difference is more than 3 m (a teleport, a desk being taken, a world reset). Why not replay every input on top of the server's position, as some games do: it needs the server to apply exactly one input per tick and both sides to use exactly the same step length, which is fragile over a real network and not worth it for walking around an office at 1.5 m/s.
2. **Chat is local by default.** A line is heard by people within 10 m of the speaker (the plan's number), shown as a bubble over the speaker and in a chat panel. A global line is for admins only (the existing announcement). Length limit, rate limit, control characters stripped, and a mute switch an admin can use.
3. **Emotes are a short fixed list** (wave, cheer, clap, nod) that the server accepts at most every few seconds and tells everyone about; each is an arm and head pose on the existing rig.
4. **Shared events are created on the server and sent to everyone at once**, so every browser shows them together. Hazel's rage (today a button that only affects the page you press it on) becomes one of these, with a cooldown.
5. **No new dependencies, no new database table** except one column for "muted".
6. **Every step** runs the earlier checks (`npm test`, `npm run typecheck`, `npm run build`, `npm run check:docs`, `npm run verify:browser:thorough`, `npm run check:mutations`, `npm run test:db`, the Docker smoke test, `verify:browser` against the Docker stack, `npm run e2e` and `npm run e2e:accounts`) plus its own proof, gets a "what it turned out to need" note here, and a read-only `claude-alt` review of anything security-sensitive.

## Risks and what answers them

| Risk | Answer |
|---|---|
| Prediction makes your person jitter or drift from the server | The threshold and the half-way pull; a browser check that counts corrections during a long walk; the reconciler is plain shared code with its own tests |
| A wrong ack (old, from a previous connection, or after a reset) yanks you around | The ack carries the tick and the input number; the client ignores one older than the newest it has used, and a connection starts its numbering again |
| Chat is a way to flood or abuse | Rate limit and length limit on the server, nothing but plain text is ever put into the page, an admin mute, and the audit log records mutes |
| Chat or labels leak who is where | Local chat is only sent to people in range; labels use names every client already has |
| Emote and chat messages are another way to flood the server | They count against the same 60 messages a second limit, and each has its own server cooldown |

### Step 1: prediction and reconciliation (done)

1. **A new server message, `ack`** (protocol version 5): `{ seq, tick, x, z, face }`, sent to a player alone, about once per tick while their person moves or the input number changes, and once a second otherwise (`GameGateway.sendAcks`). `seq` is the number of the last input the server used for that person. It is sent as an ordinary message, **not volatile**: it goes out right after the snapshot write, and Socket.IO drops a volatile message while a write is in flight (found when the first tests saw no acks at all). Clients cannot send it (the decoder refuses it, with a test).
2. **The reconciler** (`packages/shared/src/sim/prediction.ts`, plain code with its own tests): the client records where its predicted person is each time it sends input N. When an ack for N arrives it compares: a difference up to **0.5 m** is ignored (the server may use an input a tick or two longer than the client did: about 0.3 m while running), a bigger one is pulled by **half** (and the history for newer inputs is shifted the same way, so the part already corrected is not corrected again), and more than **3 m** is a snap (a teleport: a desk was taken, a world reset). An ack older than one already used, or with a non-finite number, is ignored. Why not replay every input on the server's position: it needs exactly one input per tick on both sides and identical step lengths, which is fragile and not worth it for walking.
3. **The client** (`player/control.js` `driveOnline`, `net/online.js`): your person is moved at once with the same shared `stepPlayer`, speeds (`WALK_SPEED`, `RUN_SPEED`) and quarter-metre steps as the server, inputs are sent as before (the position recorded with each is where the prediction is), acks are fed to the reconciler, and a pull or snap moves the person. Seating stays the server's call. Your person is no longer drawn from the 150 ms buffer while you steer; once you have stopped for 0.4 s it eases to the server's position again. `?nopredict` in the address switches prediction off (for comparing). `window.__sim.net.pred` counts acks, pulls and snaps and the biggest difference, for checks.
4. **Measured** in a real (very slow, software-rendered) browser against the Docker stack: with prediction the first movement shows within about a frame of the key press (22 to 264 ms at 4 to 9 frames a second); without it 369 to 1129 ms. After a 1.6 s walk the person and the server agree to within a centimetre once stopped, the server never snaps you, and the biggest disagreement was 0.45 m (before the threshold was raised from 0.4 to 0.5).
5. **Verified.** 8 reconciler tests (small difference ignored, half-pull, convergence, snap, nothing-sent, old and bad acks, history limit and reset, and a simulated network with 100 ms each way where the server never has to pull), protocol round trips and the "a client may not send an ack" test, 4 server tests (the ack carries the input number and position and never goes backwards; only the player gets it; a standing player hears about once a second; after a server-side teleport the ack says where they really are), 3 new mutation entries (all caught), and a browser check of the points in 4.
6. **Low frame rates.** The main loop limits one frame to 0.05 s, so at fewer than 20 frames a second the predicted person walks slower than the server's (which uses real time); the reconciler then pulls it forward in small steps. On a normal screen this does not happen.

### Step 2: name labels (done)

1. **What shows.** A small dark pill with the person's name floats over every person **a human is driving** (an account's person or a guest), drawn as a camera-facing sprite on the person's own body (`apps/client/src/people/nametags.js`, called each frame from `syncBody`). **Not** over the autopilot people (there would be 80 of them), **not** over yourself while you are steering, and not over anyone who is away. It is gone as soon as the person is handed back to the autopilot or removed (a guest who leaves), and follows a rename or a new look.
2. **Safe.** The name is drawn onto a canvas with `fillText`, so nothing the server sends is ever read as markup; textures are cached per name (at most 200) and a label's own material is disposed when it goes.
3. **The Names button** (HUD, next to Labels, under More options) turns them all off and on.
4. **Verified in a real browser** (two players): the label shows over the other player with the right name and is attached to their body; none over yourself while steering, none over any NPC; the button switches them off and on; when the other player leaves, the label goes with them.

### Step 3: local chat (done)

1. **Two messages and a notice** (protocol version 6): a client sends `say { text }` (at most 200 characters; a longer frame is a bad message and drops the connection), the server sends `chat { from, name, text }` to the speaker and to everyone within range, and a new private event kind, `notice`, tells one player something ("you are chatting too fast", "an admin has muted you"; shown in the chat panel, not in the shared activity log). A client cannot send `chat` (the decoder refuses it).
2. **The rules** (`apps/server/src/play/chat.ts`, apart from Nest and sockets so they can be tested alone): a line is **cleaned** first (control characters including newlines and tabs, and the invisible and direction-changing characters that can hide or reorder text, become spaces; spaces collapse; at most 200 characters; nothing left means nothing is sent); **heard within 10 m** of the speaker's person at that moment, plus the speaker; **at most 5 lines in 10 seconds** per account, then a refusal and a notice to the speaker alone; a **muted** account's lines go to nobody, not even itself, and it is told. Refused lines (empty, muted) do not use up the allowance. Every chat message also counts against the connection's 60-messages-a-second limit, so a flood still drops the connection. Chat text is **not logged** (only who muted whom is, in the audit log).
3. **Mute** is an admin switch: migration `003_muted.sql` adds `accounts.muted`; `POST /api/admin/users/:id/muted { muted }` (audited as `account.mute` / `account.unmute`); the account list says who is muted; on `/admin` each account has a Mute / Unmute button and a "muted" chip. It takes effect on the next line, with no reconnect (the flag is read from the database for each line that passes the cheap checks).
4. **The page.** Enter (or the Chat button, for touch) opens a one-line box at the bottom left; Enter sends and closes it, Escape closes it without sending; while it is open the movement and view keys do nothing and any held key is released. The last lines show in a panel that fades after 25 seconds (it stays while the box is open), and a speech bubble floats over whoever spoke for a few seconds. **Everything from the server is put in the page as text** (`textContent`, and canvas `fillText` for bubbles), never as markup. Announcements from an admin also appear in the panel (they were only in the activity log before). Logging out hides and empties the panel, so nothing is left for the next person at that computer.
5. **Verified.** 12 rule tests (cleaning, range exactly 10 m, the speaker always hears themselves, the limit and its window, mute, refused lines are free, someone not playing cannot speak), 11 tests over real sockets (who hears at 0, 6 and 14 m; leaving earshot; an unjoined connection hears nothing; cleaning; blank lines ignored; an over-long frame and a flood drop the connection; a limit of 5 with the notice to the speaker alone; mute and unmute at once; the admin route's checks and audit line), protocol round trips and the "a client may not send a chat" test, the database column, 4 new mutation entries (all caught), and in a real browser with three players (one 25 m away): Enter opens the box, typing wasd does not move you, Escape closes it, a line reaches the near player with the speaker's name and a bubble and not the far one, the bubble goes away, a line of HTML shows as text and does nothing, the limit's notice, mute and unmute, an admin announcement reaching everyone, and the panel emptied on logout.

**Review of step 3** (`claude-alt`, read-only): nothing lets a client choose what name a line comes from, send a server-only message, reach someone out of range or unjoined, or put markup in the page. Fixed from it, with tests: (1) every line used to cost a database query before the rate limit applied, so a muted or over-limit client could force about 60 a second: the cheap limit check now comes first and "muted or not" is remembered for a quarter of a second per account (so a mute still takes effect within a moment); (2) characters that print as nothing got through (hangul and braille blanks, the Arabic letter mark, variation selectors, the invisible tag characters, other spaces): now all turned into spaces, so a line made only of them is empty, and more than three combining marks in a row on a letter are cut; (3) the length cut could split an emoji: it now cuts on whole characters and the result always fits the protocol (a new shared \`clipChat\`, also used by the page); (4) Enter no longer opens chat from a link, summary, dialog or the login and character pages; (5) opening the chat box releases the touch stick as well as the keys; (6) a speech bubble's texture is freed when its speaker leaves; (7) a connection that has been taken over cannot speak; (8) right-to-left text cannot reorder against the name next to it. Left as it is: look-alike (homoglyph) names, as agreed.

### Step 4: emotes (done)

1. **A short fixed list, in the protocol** (version 7): wave, cheer, clap, nod (`EMOTE_KINDS`; the order is part of the protocol, add to the end). A client sends `emote { kind }`; the server answers everybody who is playing, near or far, with `emoted { from, kind }`. A client cannot send `emoted` (the decoder refuses it), and an index past the end of the list is a bad message.
2. **The rules** (`apps/server/src/play/emotes.ts`): one emote per account every 2.5 seconds (a second one inside that time is ignored: no reply, no kick), only for someone who is playing, and only from the list. A muted account can still emote (only chat is muted). They count against the same 60-messages-a-second limit as everything else.
3. **The page** (`people/animation.js`, `net/chat.js`): a received emote sets `p.emote` on that person for 2.6 seconds and overrides their arms and head (wave: right arm up with the forearm swinging; cheer: both arms up and a small jump when standing; clap: the forearms swing together; nod: the head nods). Walking ends an emote at once. Four buttons next to **Chat** and the keys **1 to 4** send them; the buttons rest for the cooldown (2.5 s). The keys do nothing while the chat box is open, on the login page, or in any other text box.
4. **Verified.** 3 rule tests, 5 socket tests (everyone sees it including a player 60 m away and the sender, an unjoined connection sees none, the cooldown, a bad index and a pre-hello emote drop the connection, a muted account can emote), protocol round trips and the "a client may not send emoted" test, 2 mutation entries (caught), and in a real browser with two players: typing 1 2 3 4 into the chat box does nothing, pressing 1 makes the other player see a wave with the arm up, a second key straight away is ignored, the emote ends by itself, the Cheer button works and lifts both arms, the buttons rest during the cooldown, and walking stops an emote.

### Step 5: shared events (done)

1. **Hazel's rage is one event for everybody.** Until now the "Make her angry" button only made her angry on the page it was pressed on. Online, the button sends `rage`; the server decides (**Hazel must be in the office, and only one rage a minute for the whole office**, `apps/server/src/play/shared-events.ts`) and, if it can start, sends one `event` of the new kind `rage` to everybody who is playing, who all start it at that moment (she swells and goes red for 10 seconds on every page, with the shake and steam). A rage the server started for everybody does not take over the camera of someone who is walking about; someone watching from the orbit camera follows her as before. A refused ask gets a private `notice` ("Hazel is still calming down. Try again in N s." or "Hazel isn't in the office right now."), shown in the chat panel. Offline (no server) the button works as it always did. Protocol version 8.
2. **Joins and leaves** are shared too: "Ana joined" and "Ana left" lines in everybody's activity log (the connection joining or going away, not the grace period).
3. **What was already shared, and stays so:** admin announcements (now also in the chat panel), the day change and the log lines the simulation writes (meetings starting and so on).
4. **Not done on purpose.** The lounge fighting game is not a server game yet; it stays a local picture. The plan lists it as "later" together with thrown objects (phase 6).
5. **Verified.** 2 cooldown tests, 3 socket tests (Hazel away: the asker is told and the minute is not used up; one ask reaches every player once, and a second ask is refused with a notice to that player alone; an unjoined connection is dropped), one for joins and leaves, 2 mutation entries, and in a real browser with two players: Hazel goes red on both pages at the same moment (0 to 214 ms apart), a walking player's camera is not taken over, and a second ask inside the minute is refused with a notice to that player only (when Hazel is away at the time of the run, it checks the "she isn't in" notice instead).
